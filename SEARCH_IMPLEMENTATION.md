# Реализация гибридного поиска

## Обзор

Система гибридного поиска объединяет лексический (FTS5) и семантический (векторный) поиск по проиндексированному контенту. Поиск работает с сохранёнными фрагментами страниц и документов без повторного обхода сайта на каждый запрос.

## Архитектура

### Компоненты

1. **SearchEngine** (`hybrid_search.go`) - основной модуль поиска
2. **FTS5 индекс** - полнотекстовый поиск средствами SQLite
3. **Векторное хранилище** - embeddings фрагментов (опционально)
4. **Система ранжирования** - объединение результатов обоих методов

### Схема базы данных

```sql
-- FTS5 виртуальная таблица для полнотекстового поиска
CREATE VIRTUAL TABLE fragments_fts USING fts5(
    fragment_id UNINDEXED,
    content,
    tokenize='unicode61 remove_diacritics 2'
);

-- Хранилище эмбеддингов
CREATE TABLE embeddings (
    fragment_id INTEGER PRIMARY KEY,
    model TEXT NOT NULL,           -- Название модели (nomic-embed-text, etc)
    dimension INTEGER NOT NULL,    -- Размерность вектора
    content_hash TEXT NOT NULL,    -- SHA256 хэш контента для версионирования
    vector BLOB NOT NULL,          -- Сериализованный вектор float32
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (fragment_id) REFERENCES fragments(id) ON DELETE CASCADE
);

-- Метаданные поиска
CREATE TABLE search_config (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
```

## Режимы поиска

### 1. Лексический режим (FTS5)

**Когда используется:**
- Модель эмбеддингов недоступна
- Явно задан флаг `--search-mode lexical`
- Поиск точных совпадений (ФИО, коды специальностей)

**Алгоритм:**
1. Подготовка запроса (удаление спецсимволов FTS5: `? : " * ( )`)
2. Определение типа запроса (ФИО/код или обычный текст)
3. Для ФИО/кодов: фразовый поиск `"Иванов Иван Иванович"`
4. Для текста: prefix matching с OR: `специальности* OR колледж*`
5. Ранжирование по BM25 (встроенное в FTS5)

**Пример:**
```go
query := "Какие специальности есть?"
ftsQuery := "Какие* OR специальности* OR есть*"
// SQL: SELECT ... FROM fragments_fts WHERE fragments_fts MATCH ?
```

### 2. Семантический режим (векторный)

**Когда используется:**
- Модель эмбеддингов доступна и проиндексирован контент
- Флаг `--search-mode semantic`

**Алгоритм:**
1. Генерация эмбеддинга запроса через Ollama API
2. Вычисление косинусного сходства со всеми векторами
3. Сортировка по similarity score
4. Возврат топ-N результатов

**Формула косинусного сходства:**
```
similarity(A, B) = (A · B) / (||A|| * ||B||)
где A, B - векторы запроса и фрагмента
```

### 3. Гибридный режим (по умолчанию)

**Алгоритм:**
1. Параллельное выполнение лексического и семантического поиска
2. Нормализация scores:
   - BM25: `normalized = score / max(score)`
   - Semantic: `normalized = (similarity + 1) / 2`  (из [-1,1] в [0,1])
3. Объединение с весами: `final = 0.4 * lexical + 0.6 * semantic`
4. Сортировка по итоговому score
5. Дедупликация по fragment_id

**Параметры:**
- `lexicalWeight = 0.4` - вес лексического поиска
- `semanticWeight = 0.6` - вес семантического поиска
- `limit` - максимальное количество результатов

## Дедупликация

Система исключает дублирование на двух уровнях:

### 1. По fragment_id
Если фрагмент найден и лексическим, и семантическим поиском, берётся максимальный score.

### 2. По content_hash
При индексации новых фрагментов проверяется SHA256 хэш содержимого. Если фрагмент с таким хэшем уже существует, новый не создаётся.

**Важно:** Не используется дедупликация по первым N символам, так как это приводит к потере разных документов с одинаковыми началами (например, повторяющиеся заголовки страниц).

## Управление эмбеддингами

### Создание индекса

```bash
erudit.exe --generate-embeddings
erudit.exe --generate-embeddings --embedding-model nomic-embed-text
```

**Процесс:** Проверка модели в Ollama, извлечение фрагментов, пакетная обработка (100 шт), генерация векторов, сохранение с SHA256 хэшем.

### Обновление и удаление

```bash
erudit.exe --update-embeddings
erudit.exe --clear-embeddings
```

## Ограничение контекста

Система ограничивает контекст: MaxContextChars=12000 (~3000 токенов), MaxFragments=15.

**Алгоритм:** Сортировка по relevance, добавление до лимита, передача метаданных (URL, дата, source_type, fragment_id).

**Формат:**
```
Источник: Название
Дата: 2024-10-02T14:46:36Z
URL: https://example.com

[текст]
---
```

## Тестирование

### Результаты

1. **Код специальности** (09.02.07): FTS5="09.02.07", найдено 3, время ~4.8s
2. **ФИО** (Иванов Иван Иванович): FTS5="Иванов Иван Иванович", найдено 1, время ~1.6s
3. **Общий вопрос**: FTS5=Какие* OR специальности* OR есть* OR колледже*, найдено 15, время ~8.3s
4. **Несуществующая информация**: найдено 15 релевантных, время ~7.3s

## Использование

```bash
# Автоматический режим
erudit.exe "вопрос"

# Выбор режима
erudit.exe --search-mode lexical "вопрос"
erudit.exe --search-mode semantic "вопрос"
erudit.exe --search-mode hybrid "вопрос"

# Управление
erudit.exe --search-status
erudit.exe --rebuild-fts
erudit.exe --generate-embeddings
erudit.exe --update-embeddings
erudit.exe --clear-embeddings
```

## Ограничения

1. **FTS5**: нет морфологии русского, решение - prefix matching (*)
2. **Векторы**: требуют Ollama, ~3KB на фрагмент
3. **Память**: векторы загружаются полностью
4. **Контекст**: лимит 12000 символов
